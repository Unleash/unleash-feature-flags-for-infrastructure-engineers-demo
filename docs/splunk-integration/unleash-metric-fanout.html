Unleash demo · Impact Metrics integration options

Adding Unleash Impact Metrics to an application already instrumented for Splunk

Impact Metrics requires a Prometheus-compatible store: Unleash issues PromQL queries against /api/v1/query_range on demand, when a chart is rendered or a safeguard is evaluated. Splunk Observability Cloud exposes no such API — its query interfaces are SignalFlow and SPL — so an application sending metrics only to Splunk cannot serve Impact Metrics. A Prometheus-compatible store has to be added alongside the existing Splunk integration.

Which options are available depends on one property of the existing integration, not on preference.

Which library does the application use to reach Splunk?

splunk-otel-<lang> — Splunk's OTel distribution

The application already emits OTLP. Adding a second destination is an additive change: register another exporter or reader on the existing MeterProvider. Cases A and C both apply and differ only in where the second output goes.

signalfx-<lang> — legacy client library

The application emits the SignalFx datapoint protocol, not OTLP. Reaching OTLP means changing instrumentation call sites. Case B avoids that by intercepting the existing protocol at a collector, at the cost of fidelity.

Splunk ingests OTLP natively at /v2/datapoint/otlp and maintains splunk-otel-collector, so OTel instrumentation is a supported Splunk path rather than a move away from Splunk. Verify which library is in use before choosing — it decides the question.

A

Second exporter on the collector

requires OTel SDK · buckets preserved

Precondition: the application emits OTLP. If it already sends OTLP to a collector, the change is one added exporter in the collector configuration and nothing on the application side. If it sends OTLP directly to Splunk's ingest endpoint, a collector is introduced and the application's endpoint is repointed at it. The collector retains the OTLP Histogram and passes it to both exporters independently; VictoriaMetrics accepts OTLP natively, so neither branch inherits the other's conversion. Further backends are added as additional exporters on the same pipeline.

otel-collector.yamlcase A
receivers:
  otlp:
    protocols: { grpc: {}, http: {} }

exporters:
  otlphttp/vm:
    metrics_endpoint: http://vmsingle:8428/opentelemetry/v1/metrics
    compression: gzip
    encoding: proto

  otlphttp/splunk:
    # gRPC is not supported for metrics here
    metrics_endpoint: https://ingest.${REALM}.observability.splunkcloud.com/v2/datapoint/otlp
    headers:
      "X-SF-Token": "${SPLUNK_TOKEN}"

service:
  pipelines:
    metrics:
      receivers:  [otlp]
      exporters:  [otlphttp/vm, otlphttp/splunk]

# Unleash is not in this pipeline. It reads
# the store directly:
#   PROMETHEUS_API=http://vmsingle:8428

# alt Splunk branch — native SIM, host metadata:
#   signalfx:
#     send_otlp_histograms: true   # keeps buckets

Required configuration

  • OTEL_EXPORTER_OTLP_METRICS_TEMPORALITY_PREFERENCE=delta — cumulative histograms arrive without min/max, which skews percentiles
  • Keep bucket boundaries at 31 or fewer. More than 31 boundaries and Splunk drops the datapoint
  • Splunk distro collector 0.98+. The ADOT build of the SignalFx exporter has no send_otlp_histogram and cannot carry histograms
  • Exponential histograms: VictoriaMetrics converts to vmrange buckets; Splunk documents explicit-bucket support only
B

Intercept the SignalFx protocol at a collector

any SDK · fidelity capped

Precondition: none — this is the option when the application uses the legacy SignalFx client library and re-instrumenting is not in scope. Redirect the SDK ingest URL to a local collector running signalfxreceiver; the collector forwards to Splunk unchanged and converts a copy to OTLP for VictoriaMetrics. One environment variable, no code change. Fidelity is bounded by the SignalFx datapoint model, which carries gauges, counters and cumulative counters only, so there is no histogram to preserve.

otel-collector.yamlcase B
# app-side: the only change
#   SIGNALFX_ENDPOINT_URL=http://collector:9943

receivers:
  signalfx:
    endpoint: 0.0.0.0:9943

exporters:
  otlphttp/vm:
    metrics_endpoint: http://vmsingle:8428/opentelemetry/v1/metrics

  signalfx:
    access_token: "${SPLUNK_TOKEN}"
    ingest_url:   "${SPLUNK_INGEST_URL}"

service:
  pipelines:
    metrics:
      receivers:  [signalfx]
      exporters:  [otlphttp/vm, signalfx]

# PROMETHEUS_API=http://vmsingle:8428

# ceiling on fidelity is the source protocol:
# SignalFx carries gauge, counter, cumulative
# counter. If the app ships pre-computed p95 as
# a gauge, that is what lands in both stores.

Unverified points

  • Confirm your Splunk SDK exposes a configurable ingest URL. Most do; verify yours
  • The SignalFx → OTLP type mapping the receiver applies is worth a spike — I have not verified it field by field
  • Splunk deprecated the older signalfx-forwarder Smart Agent monitor and points users at the collector's native receivers instead
  • There is no histogram to preserve here. You are mirroring faithfully, just at lower resolution than case A
C

Second reader on the MeterProvider

requires OTel SDK · buckets preserved

Precondition: the application emits OTLP, and its instrumentation code can be modified. Register a second reader on the existing MeterProvider — a Prometheus exporter serving /metrics — leaving the Splunk export path untouched. Differs from case A in that the second destination is added in the application rather than in the collector, which keeps the two read paths independent. Prometheus runs in default pull mode, with no remote-write receiver and no prometheusremotewrite exporter.

app + collector + prometheuscase C
# ---- app side: one SDK, two readers ----
# MeterProvider gets a Prometheus exporter
# (serves /metrics) AND a periodic OTLP
# exporter pointed at the collector.
OTEL_EXPORTER_OTLP_ENDPOINT=http://collector:4318
OTEL_EXPORTER_OTLP_METRICS_TEMPORALITY_PREFERENCE=delta

# ---- prometheus.yml: nothing unusual ----
scrape_configs:
  - job_name: unleash-demo-app
    scrape_interval: 15s
    static_configs:
      - targets: ['app:8080']

# ---- collector: Splunk branch only ----
receivers:
  otlp:
    protocols: { http: {} }

exporters:
  otlphttp/splunk:
    metrics_endpoint: https://ingest.${REALM}.observability.splunkcloud.com/v2/datapoint/otlp
    headers: { "X-SF-Token": "${SPLUNK_TOKEN}" }

service:
  pipelines:
    metrics:
      receivers: [otlp]
      exporters: [otlphttp/splunk]

# PROMETHEUS_API=http://prometheus:9090

Properties of this topology

  • No remote-write on the path Unleash reads. The SDK's Prometheus exporter emits _bucket/_sum/_count as the format's native representation rather than as a conversion of an OTLP histogram, so histogram_quantile() operates on complete bucket data
  • Prometheus runs with default configuration. No --web.enable-remote-write-receiver and no push endpoint
  • The two read paths are independent. A collector outage stops delivery to Splunk only; Prometheus and Unleash are unaffected. In case A a collector outage stops delivery to both stores
  • Temporality is set per exporter. Delta on the OTLP branch supplies histogram min/max to Splunk; the Prometheus exporter is cumulative by definition
  • The application owns two exporters, so metric names and attributes can diverge between them. Use one instrument and one view configuration per metric
